# topozarr review — code, docs, tests

## Context

topozarr is the modern replacement for [ndpyramid](https://github.com/carbonplan/ndpyramid).
ndpyramid predates the multiscales/geozarr conventions and hard-coded square
slippy-map tiles (reproject to EPSG:3857) for carbonplan-maps. zarr-layer
superseded carbonplan-maps and reads arbitrary zarr shapes/formats, so the
reprojection machinery is no longer required — topozarr is coarsen-only,
convention-first, and streams through a small Rust kernel.

Current state: 5161 LOC across src (1774), tests (2049), docs (477), rust (372).
202 tests pass in 8.85s. Public API is 5 objects. The library is in good shape;
this plan lists what is missing, what is broken, and what can be cut.

## Verified bugs

### 1. `method` is not validated at plan time — fails mid-write

`create_pyramid` stores `method` untouched (`coarsen.py:122-268`); the string is
only parsed by the Rust kernel on the first *coarsened* level. Level 0 is a
plain copy, so a typo writes level 0 to the store and then raises:

```
create_pyramid(ds, levels=3, method="median")  -> plan builds fine
pyramid.write(store)                            -> ValueError after '0' exists
```

This is the same failure shape as issue #26 (the reason for the exact
`topozarr-core` pin in 0.1.4): an accepted argument that explodes partway
through a write.

**Source of truth: the Rust enum, not a Python list.** Today `Method` (`lib.rs:10-31`)
and `CoarseningMethod` (`pyramid.py:29`) are two hand-maintained lists that can
drift. Validating against a Python-side tuple — or even
`typing.get_args(CoarseningMethod)` — only prevents *internal* drift; it still
cannot catch the case issue #26 actually hit, where the installed kernel lacks a
method the Python layer advertises.

Make the enum the single source and export it:

```rust
impl Method {
    const ALL: [(&'static str, Method); 5] = [
        ("mean", Method::Mean), ("max", Method::Max), ("min", Method::Min),
        ("sum", Method::Sum), ("nearest", Method::Nearest),
    ];
    fn parse(s: &str) -> PyResult<Self> { /* look up in ALL, error lists ALL */ }
    fn names() -> Vec<&'static str> { Self::ALL.iter().map(|(n, _)| *n).collect() }
}

// #[pymodule]
m.add("METHODS", Method::names())?;
```

One array now drives `parse`, the error message, and the Python-visible list.
Python then validates against `topozarr_core.METHODS` at plan time — the same
authority the write path will use, from the actually-installed core.

The `Literal` stays: static type checkers need it spelled out, and `ty` runs in
CI. Keep the two honest with a test asserting
`set(get_args(CoarseningMethod)) == set(topozarr_core.METHODS)`, which fails
loudly on a version skew instead of mid-write.

Two consequences to keep in mind:

- Any method added later lands in Rust first, then the `Literal`; the drift
  test enforces that order.
- The kernel's method set is a *superset* of what `as_datatree` can do —
  `_coarsen_chain` dispatches via `getattr(ds.coarsen(...), method)`, so any
  method without an `xarray.coarsen` equivalent needs the explicit
  `NotImplementedError` described in bug #2.

### 2. `as_datatree()` and `write()` produce different numbers

`as_datatree` is a keeper (Dask-distributed path), so this is a fix, not a cut.
Same `Pyramid`, two materialization paths, two independent divergences.

**2a — dtype promotion.** `xarray.coarsen` promotes integers to float:

```
i2 input, levels=2:
  pyramid.write(store)   -> int16   [ 8, 10, 12]        (kernel truncates)
  pyramid.as_datatree()  -> float64 [8.5, 10.5, 12.5]   (xarray promotes)
```

`pyramid.encoding` is computed from the *source* dtype (`itemsize=2`), so when
that encoding is handed to `DataTree.to_zarr` — which the docstring
(`pyramid.py:562-576`) and `docs/usage.md` both instruct — the chunks are sized
for a 2-byte dtype while the data is 8-byte.

**2b — `_FillValue` is ignored.** The kernel skips fill values
(`skipna=True`, `lib.rs:72`); `xarray.coarsen` has never heard of them:

```
u1 data, _FillValue=255, window [1, 255, 5, 6]:
  kernel   -> 4     (mean of 1, 5, 6)
  datatree -> 66    (mean of 1, 255, 5, 6)
```

Same for floats with a non-NaN fill. This is the more serious half: masked
data written through the Dask path is silently wrong, with no dtype change to
hint at it.

**Fix** — in `_coarsen_chain`, per variable, in this order:

```
mask fill -> NaN  ->  coarsen  ->  fillna(fill)  ->  astype(source dtype)
```

The restore must precede the cast: NaN cannot survive into an integer dtype.
The cast alone was verified to reproduce the kernel exactly across
`i2`/`i4`/`u1`, levels 1-2, including negatives (both truncate toward zero), so
no separate rounding rule is needed. Keeping the dtype also keeps the single
`pyramid.encoding` correct for both paths — no per-path encoding recompute.

Cost to document, not discover: the integer path now forces an `f8` dask
intermediate through the coarsen (4x memory on `u1`). Acceptable for a
Dask-distributed path, but it belongs in the docstring.

Residual divergences to document rather than chase: integer `sum` overflow
(xarray promotes to `int64`, the kernel accumulates `f64` then saturates on
cast), and `nearest`, which stays a separate implementation (`_decimate`,
`pyramid.py:543`) because `xarray.coarsen` has no such method.

**Methods xarray cannot express.** `_coarsen_chain` dispatches via
`getattr(ds.coarsen(...), method)`, so a kernel method with no `xarray.coarsen`
equivalent would surface as `AttributeError`. Declare the hole in this step
rather than acquiring an undefined one later: keep an explicit list of
expressible methods and raise `NotImplementedError` for anything else. A
non-composable method such as `mode` could not use this chained structure at
all, so the guard is the right shape whether or not one ever lands.

### 3. 2-D (curvilinear) coordinates fail with an opaque error (and are wrong on the other path)

`_coarsen_template` (`coarsen.py:38-45`) passes non-1-D coords through at native
shape, then `xr.Dataset(...)` raises from inside the template builder:

```
ValueError: conflicting sizes for dimension 'y': length 32 on 'lat' and length 16 on {...}
```

Known (`TODO.md`), but it surfaces as an internal xarray error, not a topozarr
message. The datatree path is worse: `_decimate` (`pyramid.py:556-559`) only
coarsens 1-D coords and corner-strides 2-D ones, so `nearest` there produces a
silently mis-registered grid rather than an error.

Cheapest correct fix for both: reject 2-D spatial coords at the
`create_pyramid` boundary with a clear message pointing at
`ds.drop_vars([...])`. Rejecting at the boundary covers `write`, `as_datatree`
and `_decimate` in one place. Coarsening them properly is a separate, larger
change.

### 4. `recommend_encoding` fails its own headline use case on dask

`ds.to_zarr(encoding=recommend_encoding(ds))` — the exact snippet in
`README.md`, `docs/usage.md` and the docstring — raises for most dask sources.
`Pyramid.write` never hits this (it streams regions itself), so only flat-path
users see it.

**`planning/followups.md` was stale on the cause; do not follow its fix.** It
says the recommendation "aligns the chunk, not the shard". It already aligns
the shard: `snap_chunk_to_source` (`chunking.py:110-133`) builds candidate
*shard* sizes, filters `s % cps == 0`, and returns `s // cps` as the chunk.
Re-measured against the current code:

```
2000x2000 f4, ideal chunk 362, cps=4
  dask  500 -> chunk 375 shard 1500   500 % 1500 != 0   FAIL
  dask  750 -> chunk 375 shard 1500   750 % 1500 != 0   FAIL
  dask  256 -> chunk 384 shard 1536   256 % 1536 != 0   FAIL
  dask 1000 -> chunk 250 shard 1000  1000 % 1000 == 0   OK
```

Real cause: `safe_chunks` needs the write unit to **divide** the dask block
(`dask_chunk % shard == 0`). The candidate set admits both divisors and
multiples of `src_chunk`; every multiple fails. And restricting to divisors
alone does not help — the `chunk >= 128` floor then rejects all of them
(`500/4 = 125`, `256/4 = 64`).

The only lever that actually works is flexing `chunks_per_shard` **down**:
pick the largest `cps` whose shard divides `src_chunk` with `chunk >= 128`.
Verified against the same four rows:

```
  dask  500 -> cps 2  shard  500  chunk 250   OK
  dask  750 -> cps 2  shard  750  chunk 375   OK
  dask  256 -> cps 1  shard  256  chunk 256   OK
  dask 1000 -> cps 4  shard 1000  chunk 250   OK
```

Two decisions this forces:

- **Scope.** `create_pyramid` routes its per-level encoding through
  `recommend_encoding`, so this moves `pyramid.encoding` for chunked sources
  too, and re-baselines
  `test_pyramid_level0_encoding_matches_recommend_encoding`. Recommendation:
  apply it on both paths rather than forking behavior — a shard that divides
  `src_chunk` still gets each source chunk read once, because
  `copy_region_shape` widens the region to `lcm(shard, source_chunk)`.
- **Silence.** Flexing overrides an explicitly passed `chunks_per_shard`.
  Recommendation: treat the user's value as an upper bound, only flex when a
  source chunking is detected, and document it — the alternative (flex only
  when `cps` is the default) is subtler and harder to explain.

### 5. `write` drops variables over exactly one spatial dim

Found while testing step 2's parity, not by this review. A variable over one
spatial dim and one other (`profile(time, x)`) is legal input and is planned
into every level template, but `Pyramid._spatial_vars` selects only variables
carrying *both* spatial dims. Nothing computes the rest, so above level 0 the
template placeholder is written verbatim:

```
profile(time, x) i2, levels=2
  level 0              ->  i2, exact        (plain copy)
  level 1              ->  f4, all NaN      (placeholder, never reduced)
  as_datatree level 1  ->  i2, correct means
```

Silent all-NaN data, float-promoted off the source dtype. Level 0 being correct
is what makes it easy to miss.

Two ways out: coarsen these along whichever spatial dims they carry (matching
`as_datatree`), or reject them at `create_pyramid` the way curvilinear coords
are. Coarsening is the better answer — a per-row or per-column statistic
alongside a raster is a reasonable thing to store, and the datatree path already
does it correctly. Rejecting is defensible only if the kernel cannot be pointed
at a subset of axes.

Pinned by `tests/test_pyramid.py::test_as_datatree_matches_write_partly_spatial_var`
as `xfail(strict=True)`, so it fails loudly once the write path is fixed.

## Cuts (simplicity)

### Kept, by decision

- **Level pipelining / fusion** (`_make_fused_reduce_hook`,
  `_compute_use_fusion`, `_fusion_buffers`, ~150 lines): real speedup, stays as
  is. Note it is not tied to any Rust write path — the `io="rust"` path was
  removed in 0.1.5 (`bd1b221`); fusion is pure Python in `pyramid.py` and saves
  re-reading each written level back from the store. Keeping it also keeps the
  `psutil` dependency, which only `default_max_workers` and the fusion budget
  use.
- **`as_datatree()`**: stays as the Dask-distributed path. Bug #2 is fixed
  in place instead.

### Optional, low priority

**`stats=True` / `RegionTimer`** — ~40 lines in `engine.py` plus a `timer=`
parameter threaded through `copy_array`, `downsample_level`, `_write_regions`,
`_write_var` and `write`. Instrumentation left from the removed bench harness.
Worth a look only if the plumbing gets in the way of another change; not worth
a dedicated PR. With fusion kept, its `reduce_s` caveat in the `write`
docstring stays relevant, which is a mild argument for keeping it.

## Missing

### 1. Position against ndpyramid, explicitly

Nothing in `README.md` or the docs mentions ndpyramid, or says that topozarr
**does not reproject or regrid**. ndpyramid users arriving here will look for
`pyramid_reproject` / `pyramid_regrid`. One short README section: what moved
(coarsen → `create_pyramid`, tiles → zarr-layer reads any grid), and what to
do instead (rioxarray / odc-geo / xesmf upstream of `create_pyramid`).

### 2. `mode` (majority) coarsening — dropped (2026-09-02)

`nearest` is a half-measure for categorical rasters: a class that never lands on
a window corner vanishes at coarse zoom. `mode` is non-composable, so its levels
must reduce from level 0 rather than from the level above — which changes the
write path's read pattern, not just the kernel.

**Cut by decision, along with its design doc.** It was the largest item here and
the only one reaching into the write path's read pattern; `nearest` covers the
categorical case for now. Step 2's `NotImplementedError` guard means picking it
back up later needs no rework of the datatree path. Recovering the design means
recovering `planning/mode-coarsening.md` from git history (deleted in the step 2
branch).

### 3. Per-variable coarsening method

`method` is per-pyramid. A dataset with a continuous variable and a mask needs
`mean` for one and `nearest` for the other, and today must be written as
two pyramids.

### 4. Coordinate array chunking

Level coords are written through `template.drop_vars(...).to_zarr(...)`
(`pyramid.py:339`) with xarray defaults — a single chunk covering the whole
coordinate. Fine at 10^4, a multi-MB blocking read at 10^7.

### 5. No recovery from a partially written pyramid

`write()` has no cleanup or resume: a failure partway through leaves the
already-written levels in the store and nothing records how far it got. This
plan cites that failure shape twice (bug #1, and issue #26 in the 0.1.4 notes)
but both fixes only remove *triggers* — the underlying state is unchanged, and
any mid-write failure (network, OOM, interrupt) reproduces it. `TODO.md`
already carries "overwrite/resume semantics for partially written pyramids
(e.g. skip regions already present when `mode='a'`)"; it deserves to be its own
item rather than a footnote.

### 6. CHANGELOG.md

Backfill from git tags in Keep a Changelog format (this was `TODO.md`'s top
entry, before that file was removed).
`docs/releases.md` covers 0.1.3 onward and explicitly defers earlier history to
GitHub releases, so this is low value, but it is the one `TODO.md` entry
nothing else in this plan touches.

### 7. CI gaps

Wheels ship for macOS and Windows (`publish.yml`), only Ubuntu is tested. No
coverage reporting. Both already in `TODO.md`.

## Tests

Healthy: 202 tests, 8.85s, all green. Hypothesis property tests cover encoding
invariants and spatial transforms; kernel semantics (dtypes, skipna, fill,
trim, nearest composition) are covered in Rust unit tests *and* Python parity
tests against `xarray.coarsen`; S3 via moto and icechunk both exercised;
geozarr conformance is checked against `geozarr-toolkit` behind a marker.

Gaps, in order:

1. **No test rejects an invalid `method`** — because nothing validates it
   (bug #1). Add once validation lands.
2. **No test compares `as_datatree()` against `write()` for integer dtypes or
   for `_FillValue` data** — `test_as_datatree_matches_native` uses `f4` with
   no fill, which is exactly why both halves of bug #2 are invisible. The
   replacement should be parametrized over dtype × method × fill/no-fill and
   assert the two paths agree element-wise, not just in shape.
3. **No curvilinear-coordinate test** — bug #3 is uncovered.
4. **No `mode="a"` incremental-append test** beyond the level-subset cases
   (e.g. adding a variable to an existing pyramid), and nothing covers the
   store state left behind by a mid-write failure (missing #5).
5. **Only 3 conformance tests**, and they run against an in-memory pyramid of
   one shape. A parametrized sweep (sparse factors, extra dims, non-4326 CRS)
   would guard the metadata surface that zarr-layer actually consumes.
6. **No coverage measurement**, so gaps like #2 are found by reading, not by
   tooling.

## Verification

Every step:

- `uv run pytest -n auto` (202 tests today; each step adds cases)
- `uv sync --group conformance && uv run pytest -n auto -m conformance`
- `uv run pre-commit run --all-files` and `uv run ty check src/`

Per step:

- **Step 1**: `cargo test` in `core/`, then rebuild the kernel
  (`uv sync --all-groups`) before the Python tests — `METHODS` does not exist
  until the extension is rebuilt, so the drift test fails confusingly against a
  stale wheel. Confirm `create_pyramid(ds, method="median")` now raises at plan
  time with nothing written to the store.
- **Step 2**: for each dtype × method × fill/no-fill, assert
  `pyramid.as_datatree()[str(lvl)].ds[name].values` equals the array `write()`
  put in the store, element-wise, for every level.
- **Step 3**: write a dask-backed dataset through `recommend_encoding` to a
  `MemoryStore` *without* `safe_chunks=False`, across the four dask chunk sizes
  tabulated above.

**Regression gate, and its exceptions.** For changes touching `write`,
`create_pyramid(...).write(store)` must be byte-identical before/after on a
multi-variable, multi-level, extra-dims dataset (compare `arr[:]` per level,
not just metadata), with fusion both auto-enabled and forced off.

This gate does **not** apply to steps 2 and 3, which change output by design:
step 2 changes `as_datatree` values and dtypes, step 3 changes
`pyramid.encoding` (and therefore chunk/shard layout) for chunked sources. For
those two, the gate is instead: level *data* unchanged for an **unchunked**
source, and the new behavior pinned by the step's own tests.
